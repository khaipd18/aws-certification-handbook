# SOA-C03 — Amazon EC2 for CloudOps

> Thuộc **Domain 1: Monitoring, Logging, Analysis, Remediation, and Performance Optimization (22%)** và **Domain 2: Reliability and Business Continuity (22%)**: đổi instance type, placement group, xử lý lỗi SSH, metric, status check, recovery, hibernate, lập lịch tắt/bật.
> Ký hiệu: `[+]` = bổ sung ngoài slide · `❓` = cần kiểm chứng · `⚠️` = lỗi thời.

---

## 1. TL;DR

- **Đổi instance type** chỉ làm được với instance **EBS-backed** và phải **Stop** trước. Stop làm mất Public IPv4 (trừ Elastic IP) và mất dữ liệu instance store.
- **Placement group**:
  - **Cluster**: một AZ, độ trễ thấp, tới 10 Gbps single-flow.
  - **Spread**: tối đa **7 instance đang chạy mỗi AZ**.
  - **Partition**: tối đa **7 partition mỗi AZ**, chứa hàng trăm instance (HDFS, Cassandra, Kafka).
- **Lỗi SSH**: `Unprotected private key file` → `chmod 400`; `Permission denied` → sai username/key; `Connection timed out` → SG / NACL / route table / public IP / CPU quá tải.
- **EC2 Instance Connect** đẩy SSH public key dùng một lần, tồn tại **60 giây** trong metadata. **EIC Endpoint** cho SSH/RDP vào instance private mà không cần IGW, NAT hay public IP.
- **CloudWatch**: Basic 5 phút, Detailed 1 phút. **RAM, disk space, log không có sẵn**, phải cài **Unified CloudWatch Agent** (namespace `CWAgent`).
- **Status check**: System (hạ tầng AWS) → **Stop & Start**; Instance (OS/cấu hình) → **Reboot** hoặc sửa cấu hình; Attached EBS → kiểm tra volume.
- **Hibernate**: RAM ghi vào root EBS **đã mã hóa**; Linux RAM < 150 GiB; tối đa 60 ngày; chỉ bật được **lúc launch**.
- **Instance Scheduler on AWS** là một AWS Solution triển khai bằng CloudFormation (tag + Lambda + DynamoDB), tiết kiệm tới ~70% cho tài nguyên chỉ chạy giờ hành chính.

## 2. Core Concepts

### Đổi instance type
- **Là gì:** Stop → Change instance type → Start; giữ instance ID, EBS và private IP.
- **Dùng khi nào:** right-sizing sau khi xem metric, scale dọc khi ứng dụng không scale ngang được.
- **Vì sao quan trọng:** instance store-backed không đổi được type. Type mới phải tương thích AMI: cùng kiến trúc (x86_64 / arm64), có driver ENA và NVMe khi chuyển sang Nitro; thiếu driver thì instance không boot.

### Placement Groups
- **Là gì:** điều khiển cách EC2 đặt instance lên phần cứng. **Cluster** gom trong một AZ; **Spread** mỗi instance một rack riêng; **Partition** chia thành nhóm rack tách biệt.
- **Dùng khi nào:** Cluster cho HPC, cần độ trễ thấp nhất; Spread cho vài instance critical cần cô lập lỗi; Partition cho hệ phân tán biết topology (instance đọc partition qua metadata).
- **Vì sao quan trọng:** Cluster dễ gặp **Insufficient Capacity** → stop toàn bộ rồi start lại cùng lúc, dùng một instance type, launch một request. Spread level `host` chỉ có trên Outposts.

### Xử lý lỗi SSH
- **Là gì:** ba nhóm lỗi: quyền file key, xác thực (username/key), mạng (timeout).
- **Dùng khi nào:** timeout thì kiểm tra theo thứ tự SG → NACL (stateless, nhớ outbound ephemeral 1024–65535) → route table có IGW → public IPv4 → tải CPU.
- **Vì sao quan trọng:** "một số IP vào được, IP khác không" → SG/NACL. "Hôm qua được, nay không ai vào được" → nghi status check, sshd hỏng, ổ đầy; dùng **EC2 Serial Console** hoặc system log / screenshot.

### EC2 Instance Connect & EIC Endpoint
- **Là gì:** Instance Connect đẩy key tạm 60 giây qua API `SendSSHPublicKey` (ghi CloudTrail). EIC Endpoint là endpoint trong VPC, mở tunnel bằng `OpenTunnel` tới instance private qua SSH (22) hoặc RDP (3389).
- **Dùng khi nào:** Instance Connect qua console → SG phải cho phép dải IP `EC2_INSTANCE_CONNECT` của Region (ip-ranges.json hoặc managed prefix list). EIC Endpoint → SG endpoint cho outbound 22 tới instance, SG instance cho inbound 22 từ SG endpoint.
- **Vì sao quan trọng:** EIC Endpoint thay bastion host. `[+]` Condition key `ec2-instance-connect:maxTunnelDuration` từ 1 tới 3,600 giây (mặc định 3,600). Quota cố định: 5 endpoint mỗi account mỗi Region, 1 mỗi VPC, 1 mỗi subnet, 20 kết nối đồng thời mỗi endpoint.

### CloudWatch metrics cho EC2
- **Là gì:** metric có sẵn trong `AWS/EC2`: CPU, credit (họ T), network, status check, disk (**chỉ instance store**). Custom metric qua `PutMetricData`: standard 1 phút, high resolution 1 giây.
- **Dùng khi nào:** cần phản ứng nhanh (scale, alarm 1 phút) → bật Detailed Monitoring.
- **Vì sao quan trọng:** metric EBS nằm ở `AWS/EBS` (`VolumeReadOps`, `VolumeQueueLength`, `BurstBalance`). Metric không lên thường do instance role thiếu `cloudwatch:PutMetricData`.

### Unified CloudWatch Agent & procstat
- **Là gì:** agent trên EC2 hoặc server on-prem thu thập metric hệ thống (`mem_used_percent`, `disk_used_percent`) và đẩy log lên CloudWatch Logs; config lưu ở **SSM Parameter Store**.
- **Dùng khi nào:** đề nhắc memory, disk space, swap, log từ trong OS. **procstat** để đo từng tiến trình (Linux và Windows), chọn bằng `pid_file`, `exe` hoặc `pattern`; metric có tiền tố `procstat_`.
- **Vì sao quan trọng:** instance role cần `CloudWatchAgentServerPolicy`. Cài hàng loạt bằng Run Command (`AWS-ConfigureAWSPackage`, `AmazonCloudWatch-ManageAgent`). Private subnet không có NAT cần interface endpoint `monitoring` và `logs`.

### Status checks
- **Là gì:** **System** (host vật lý, nguồn, mạng của AWS), **Instance** (OS, cấu hình mạng, hết RAM, filesystem hỏng), **Attached EBS** (volume gắn kèm). Metric 1 phút, 0 = pass, 1 = fail.
- **Dùng khi nào:** System fail → **Stop & Start** để chuyển host (reboot không đổi host). Instance fail → reboot hoặc sửa OS.
- **Vì sao quan trọng:** Stop & Start làm mất instance store và đổi public IPv4. Xem thêm AWS Health Dashboard để biết có sự kiện bảo trì.

### Auto recovery
- **Là gì:** khôi phục instance khi System check fail, **giữ** instance ID, private IP, Elastic IP, metadata, placement group. Có hai cách: **simplified automatic recovery** (bật mặc định trên instance type được hỗ trợ) và **CloudWatch alarm action `recover`**.
- **Dùng khi nào:** cần giữ IP và có thông báo SNS → alarm `recover` + SNS. Không cần giữ IP, muốn thay mới hoàn toàn, chịu được lỗi AZ → **ASG min = max = desired = 1**.
- **Vì sao quan trọng:** ⚠️ Lỗi thời: "recovery không chạy với instance có instance store" → nay alarm-based recovery hỗ trợ instance store ở một số họ (M3, C3, R3, X1, X1e, X2idn, X2iedn), nhưng dữ liệu RAM và instance store bị mất. Simplified recovery không áp cho instance trong ASG, có EFA, hoặc đang có scheduled maintenance.

### EC2 Hibernate
- **Là gì:** ghi RAM ra root EBS rồi stop; khi start, nạp lại RAM nên process và cache còn nguyên.
- **Dùng khi nào:** process chạy lâu, khởi tạo lâu, cache cần warm.
- **Vì sao quan trọng:** điều kiện: root là EBS, **đã mã hóa**, đủ lớn chứa RAM; Linux RAM < 150 GiB (Windows ≤ 16 GiB); không hỗ trợ giữ hibernate quá 60 ngày; bật **lúc launch**, không bật được cho instance có sẵn. Khi hibernate vẫn trả phí EBS và Elastic IP.

### Instance Scheduler on AWS
- **Là gì:** AWS Solution (không phải service) triển khai qua CloudFormation; lịch lưu trong DynamoDB, Lambda đọc tag rồi start/stop EC2, ASG, RDS.
- **Dùng khi nào:** tắt môi trường dev/test ngoài giờ trên nhiều account và Region, ít code.
- **Vì sao quan trọng:** tài liệu ước tính tiết kiệm tới ~70% (168 giờ/tuần giảm còn 50 giờ). Chỉ tài nguyên được tag mới bị ảnh hưởng.

### `[+]` Công cụ debug & bảo vệ instance
- **Là gì:** **EC2 Serial Console** (instance Nitro, bật ở mức account, OS cần user có password), **Get System Log**, **Get Instance Screenshot**.
- **Dùng khi nào:** instance không boot, sshd hỏng, network cấu hình sai, cần xem kernel panic.
- **Vì sao quan trọng:** bảo vệ thêm bằng **IMDSv2 required** (chống SSRF lấy credential), **Termination Protection / Stop Protection**. Termination Protection không chặn ASG terminate hoặc shutdown từ OS khi shutdown behavior = terminate.

### `[+]` Tenancy & mạng nâng cao
- **Là gì:** tenancy `default`, `dedicated` (Dedicated Instance), `host` (Dedicated Host thấy socket/core). ENI chuyển được giữa instance cùng AZ. ENA tới 100 Gbps; EFA cho HPC/ML.
- **Dùng khi nào:** license BYOL theo socket/core → Dedicated Host. IP nổi failover → ENI. HPC → EFA + cluster placement group.
- **Vì sao quan trọng:** đề hay gài "license theo core" để loại Dedicated Instance.

## 3. Key Terms

| Term | Giải thích ngắn | Dấu hiệu trong đề |
|---|---|---|
| Cluster placement group | Một AZ, độ trễ thấp nhất | "HPC", "lowest latency", "10 Gbps" |
| Spread placement group | Mỗi instance một rack, 7/AZ | "critical instances, isolate failures" |
| Partition placement group | Nhóm rack tách biệt, hàng trăm node | "Cassandra, Kafka, HDFS" |
| EC2 Instance Connect | Key SSH tạm 60 giây | "no long-lived keys", "audit in CloudTrail" |
| EIC Endpoint | SSH/RDP tới instance private | "no IGW, no NAT, no bastion" |
| Detailed Monitoring | Metric EC2 mỗi 1 phút | "1-minute granularity" |
| Unified CloudWatch Agent | Metric hệ thống + log | "memory", "disk space", "application logs" |
| `CWAgent` | Namespace mặc định của agent | "metric not in AWS/EC2" |
| procstat | Metric theo tiến trình | "monitor a specific process" |
| `StatusCheckFailed_System` | Lỗi hạ tầng AWS | "underlying host", "hardware failure" |
| Alarm action `recover` | Khôi phục giữ ID/IP | "retain IP addresses and metadata" |
| Hibernate | Giữ RAM qua lần stop | "preserve in-memory state", "warm cache" |
| Instance Scheduler on AWS | Lịch start/stop theo tag | "stop outside business hours, multi-account" |
| EC2 Serial Console | Truy cập console nối tiếp | "cannot boot, cannot SSH" |

## 4. Dễ nhầm & bẫy đề

### 4.1 Các cặp dễ lẫn

| Concept A | Concept B | Khác nhau ở đâu | Mẹo nhớ |
|---|---|---|---|
| Reboot | Stop & Start | Reboot giữ host; Stop & Start chuyển host mới | System check fail → Stop & Start |
| System status check | Instance status check | System: hạ tầng AWS; Instance: OS/cấu hình của bạn | "Underlying host" → System |
| Alarm `recover` | ASG min=max=1 | Recover giữ ID/IP; ASG thay instance mới, khác IP | "Retain IP" → recover |
| Metric `AWS/EC2` | Unified CloudWatch Agent | Có sẵn CPU/network/status; RAM, disk space, log thì không | Memory → agent |
| `AWS/EC2` DiskReadOps | `AWS/EBS` VolumeReadOps | Disk metric EC2 chỉ cho instance store | IOPS của EBS → `AWS/EBS` |
| Instance Connect | EIC Endpoint | Instance Connect cần public IP và SG mở dải AWS; endpoint cho instance private | Private subnet → EIC Endpoint |
| EIC Endpoint | Session Manager | Endpoint dùng SSH thật, không cần agent; Session Manager cần SSM Agent + role, không mở port, không key | "No inbound ports, session logs" → Session Manager |
| Stop | Hibernate | Stop mất RAM; Hibernate ghi RAM ra EBS mã hóa | "Preserve RAM" → Hibernate |
| Dedicated Instance | Dedicated Host | Host thấy socket/core, gắn host cố định | BYOL theo core → Dedicated Host |

| Từ khóa trong đề | Chọn | Ghi chú |

## 5. Câu hỏi tình huống

**Câu 1.** Cụm Cassandra 120 node cần hạn chế lỗi phần cứng lan sang nhau, và mỗi node phải biết nhóm hạ tầng của mình để đặt replica. Chọn gì?
- A. Cluster placement group
- B. Spread placement group
- C. Partition placement group
- D. Trải qua nhiều AZ, không dùng placement group

<details><summary>Đáp án</summary>

**C.** Partition tách nhóm rack, hàng trăm instance, node đọc partition qua instance metadata.
- A sai: dồn vào một AZ, rủi ro lỗi chung.
- B sai: giới hạn 7 instance mỗi AZ.
- D sai: không cho node biết topology rack.
</details>

**Câu 2.** Instance báo `StatusCheckFailed_System = 1`. Reboot nhiều lần không hết. Làm gì?
- A. Reboot từ trong OS
- B. Stop rồi Start instance
- C. Đổi Security Group
- D. Detach rồi attach lại EBS

<details><summary>Đáp án</summary>

**B.** Stop & Start chuyển instance sang host vật lý mới.
- A sai: reboot giữ nguyên host.
- C sai: SG không liên quan lỗi host.
- D sai: lỗi volume thể hiện ở `StatusCheckFailed_AttachedEBS`.
</details>

**Câu 3.** (Chọn 2) Cần tự khôi phục instance khi host lỗi, **giữ nguyên private IP, Elastic IP và placement group**, đồng thời báo cho đội trực. Chọn hai thành phần.
- A. CloudWatch alarm trên `StatusCheckFailed_System` với action `recover`
- B. ASG min = max = desired = 1
- C. SNS topic gắn vào alarm action
- D. Lambda tự viết terminate và launch instance mới
- E. Alarm trên `CPUUtilization`

<details><summary>Đáp án</summary>

**A, C.** Recover giữ ID, IP, metadata; SNS gửi thông báo.
- B sai: ASG tạo instance mới, mất private IP và EIP.
- D sai: instance mới, nhiều công sức.
- E sai: CPU không phản ánh lỗi host.
</details>

**Câu 4.** Cần theo dõi memory và disk space của 200 EC2. Cách đúng nhất?
- A. Bật Detailed Monitoring
- B. Cài Unified CloudWatch Agent, config lưu ở Parameter Store, gắn role có `CloudWatchAgentServerPolicy`
- C. Đọc metric `MemoryUtilization` trong `AWS/EC2`
- D. Bật EC2 Instance Connect

<details><summary>Đáp án</summary>

**B.**
- A sai: chỉ tăng tần suất metric có sẵn, không thêm RAM.
- C sai: `AWS/EC2` không có metric memory.
- D sai: công cụ truy cập, không phải monitoring.
</details>

**Câu 5.** Điều nào **không** phải điều kiện của EC2 Hibernate?
- A. Root EBS volume phải mã hóa
- B. Instance Linux có RAM dưới 150 GiB
- C. Instance phải nằm trong placement group
- D. Hibernation phải được bật lúc launch

<details><summary>Đáp án</summary>

**C.** Hibernate không yêu cầu placement group.
- A, B, D đều là điều kiện thật theo docs.
</details>

**Câu 6.** Admin cần SSH vào instance ở private subnet. VPC không có IGW, NAT; công ty không muốn duy trì bastion và vẫn muốn dùng SSH client quen thuộc. Chọn gì?
- A. Gán Elastic IP
- B. Tạo EC2 Instance Connect Endpoint
- C. Mở port 22 cho `0.0.0.0/0`
- D. EC2 Instance Connect từ console, không endpoint

<details><summary>Đáp án</summary>

**B.** EIC Endpoint tạo tunnel vào instance private, không cần IGW, NAT hay public IP.
- A sai: VPC không có IGW nên EIP vô dụng, lại phơi instance ra Internet.
- C sai: vừa không an toàn vừa không có đường vào.
- D sai: cần public IP và đường Internet.
</details>

**Câu 7.** (Chọn 2) SSH vào instance mới trong public subnet bị `Connection timed out`. Hai nguyên nhân khả dĩ nhất?
- A. File `.pem` có quyền 644
- B. SG không cho phép inbound TCP 22 từ IP người dùng
- C. Route table của subnet thiếu route tới IGW
- D. Sai username
- E. Chưa cài CloudWatch Agent

<details><summary>Đáp án</summary>

**B, C.** Timeout là gói tin không tới được instance.
- A sai: gây lỗi `Unprotected private key file`.
- D sai: gây `Permission denied`, tức đã tới được instance.
- E sai: không liên quan kết nối.
</details>

**Câu 8.** Cần tự tắt EC2 và RDS của môi trường dev ngoài giờ trên nhiều account và Region, ít code nhất. Chọn gì?
- A. Lambda tự viết + EventBridge ở từng account
- B. Instance Scheduler on AWS triển khai bằng CloudFormation, gắn tag cho tài nguyên
- C. Scheduled action của Auto Scaling cho mọi tài nguyên
- D. Mua Reserved Instances

<details><summary>Đáp án</summary>

**B.** Solution có sẵn, lịch tập trung trong DynamoDB, hỗ trợ EC2/ASG/RDS, cross-account.
- A sai: phải tự viết và duy trì.
- C sai: chỉ áp cho ASG, không cho RDS hay EC2 lẻ.
- D sai: giảm giá chứ không tắt tài nguyên; trả cả khi không dùng.
</details>
